# The README hero

`hero.gif` and `hero.mp4` are the same recording — one tape, two encodes. It is a
**recorded real run**, not a mock-up: two people, one file, and the moment the
tool earns its keep.

| file | why |
|---|---|
| `hero.gif` (~1.6 MB) | embedded in the README — **GitHub strips `<video>` and does not autoplay MP4**, so the GIF is the only thing that plays on the repo page |
| `hero.mp4` (~0.9 MB) | the pausable, shareable one — drop it in Slack, a forum post, a blog; smaller and sharper than the GIF |
| `quadrant.svg` (4 KB) | the positioning on its own, for anywhere the GIF never plays (GitHub mobile, PyPI, autoplay off) |

Everything else here is about how the recording is produced and re-made.

## Why this scenario

A Perforce user's pain is not "Git is slow" — P4 sync is lazy too. It is:

| their situation | P4 | BlackGit |
|---|---|---|
| want to try an idea, but branching is a ceremony | ✗ | `git checkout -b` locally |
| every small change needs the server | ✗ | commit locally, push whenever |
| two people edit the same `.umap`, merge is guaranteed to break | ✓ only via exclusive checkout | ✓ same lock, plus real Git branches |

So the demo argues **"locks and branches are no longer either/or"**, and the
last beat is the whole point: bob's local branch and commit are untouched,
only the `push` is refused — and git prints who holds the lock.

## Beats

| time | on screen | what it proves |
|---|---|---|
| 0-6s | `du -sh` the 1.4 GB server repo → `git black clone` → `du -sh .git` = **168 KB** | you do not download it |
| 6-11s | `git black ls assets/levels` lists three `.umap` files, `.git` unchanged | browse everything, download nothing |
| 11-16s | `git black follow assets/levels/city.umap` → `.git` becomes 60 MB | take exactly what you work on |
| 16-20s | alice `lock` → **locked by alice**; bob `lock` → **already locked by alice** | the `p4 edit` reflex, unchanged |
| 20-30s | bob branches, edits, commits — all instant, all local | the lock does not touch local work |
| 30-48s | `git push` → `! [remote rejected] … (file lock: … (locked by alice))` | only the push is guarded, and it says why |

## Every number is real

The repo is generated by `../make-fixture.sh`: real incompressible blobs
(`/dev/urandom`), real history, ~1.4 GB. The recording runs the real client
against the real server. Nothing on screen is typed in by hand — including the
`1.4G`, which is `du` output.

`record.sh` fails loudly if the take is wrong: if `refs/heads/twilight` exists
afterwards, bob's push was *not* refused and the GIF would be showing the
opposite of the claim.

## Re-recording

```bash
brew install vhs ffmpeg          # once
./../make-fixture.sh             # rebuild the 1.4 GB repo (~10s)
./record.sh                      # reset state, warm the server, run vhs
```

The tape works through `/tmp/bg`, a short real directory holding the fixture
behind symlinks — git prints absolute paths in its own messages
(`Initialized empty Git repository in …`), and the fixture's real path is long
enough to wrap every line on screen. `record.sh` rebuilds that directory.

Credentials come from `as-user.sh`. The empty `credential.helper` entry first
is load-bearing: it drops the machine's global `osxkeychain` helper, so the
tape authenticates as whoever it says (alice, then bob) instead of whoever
happens to be cached in the keychain.

`BLACKGIT_QUIET=1` hides the client's trace of the underlying git commands;
everything the program itself prints stays.

## Encoding

`record.sh` runs the tape twice — once as written (GIF), once with the `Output`
line rewritten to `.mp4` — so the two encodes can never drift apart.

**GIF.** vhs writes ~2.5 MB / 48 s; the committed one is re-encoded to 15 fps /
980 px / 64 colours (~1.6 MB), the smallest change that still reads
comfortably. `palettegen=stats_mode=diff` is the part that matters: most frames
are identical while the demo waits, so per-frame palette churn is what blows the
file up. The MP4 keeps the full 1180 px, because a GIF at that size costs 60%
more for no visible gain.

**MP4.** H.264 High / yuv420p, `-crf 22`, `-movflags +faststart`, no audio
track. yuv420p is the one that actually plays in QuickTime, phones and Slack.
`+faststart` puts the moov atom up front so it starts playing without a full
download. No audio track because the recording has none, and an empty track
only trips some players.

## quadrant.svg

The animation is the primary asset, but a GIF is a still image in GitHub's
mobile view, on PyPI, and anywhere autoplay is off. `quadrant.svg` states the
positioning on its own — exclusive file locks vs local branches, with Perforce,
Git, a shared folder and BlackGit — in about 4 KB, so the README still lands if
the animation never plays. It is in English only, so the same file works in
both READMEs and anywhere else it gets pasted.
